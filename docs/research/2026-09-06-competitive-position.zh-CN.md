# DevMap 竞争优势核查（2026-09-06）

结论：DevMap 有真实用途和可辨认的产品差异，但现有证据不足以认定它拥有独特、难以替代的竞争优势。下一阶段应验证用户收益，而不是继续扩大“多 Agent 指挥台”的功能范围。

## 方法与范围

DevMap 基线是本地 main 的 4777a79；读取 README、src/dock.rs、src/mcp.rs 及已有测试。安装改进在本次分支验证，不能提前算作已上线能力。竞品依据以下第一方文档和公开仓库，本次没有安装运行竞品，也没有测量速度、稳定性或付费转化。“未见说明”不代表功能不存在。用户说的 Codex WorkTray 在本报告中按 Codex 原生 Worktrees 理解。

## 已确认的竞争重叠

| 能力 | DevMap 当前基础 | Vibe Kanban | ATC Kanban | Codex Worktrees |
| --- | --- | --- | --- | --- |
| 多工作区 | 从 Git 读取本机仓库 worktrees | 创建任务工作区 | 任务 worktree 隔离 | 同项目多个任务并行 |
| 任务/Agent 关联 | 依赖宿主提供观察，准确路径关联 | 工作区、会话、执行器关联 | 注册、认领、状态、锁 | 原生任务与工作区关联 |
| MCP | 地图事实、计划、需求/决策/证据接口 | 工作区、任务、会话管理 | 协调与任务流程工具 | 此页没有建立对等外部地图 MCP 能力 |
| 合入目标 | 已记录计划与事实分开 | 显示和更改目标分支 | 基础分支与评审合并 | Handoff/原生 Git 工作流 |
| 执行协调 | 不执行测试、merge、push 或队列 | 启动会话、代码审查、Git 操作 | 锁、依赖 DAG、评审 squash merge | 原生创建与切换工作区 |
| 一条命令启动 | 本次新增打包流程，尚未公开发布 | npx 已有文档 | npx 已有文档 | 宿主内置 |

Vibe Kanban 的 MCP 已能管理工作区和会话、启动不同执行器；多模型兼容与 MCP 本身不构成差异。[MCP 文档](https://vibekanban.com/docs/integrations/vibe-kanban-mcp-server)

Vibe Kanban 也提供当前/目标分支、改动数、领先/落后与冲突状态，支持调整目标分支，以及 PR、rebase 等操作。此前将“知道准备合到哪里”视为 DevMap 独有是不准确的。[Git 操作文档](https://www.vibekanban.com/docs/workspaces/git-operations)

ATC 的公开 README 描述 npx、MCP、实时看板、任务锁、依赖 DAG、健康检查和评审合并。其工作流协调范围比 DevMap 当前只读地图更广；这不等于已经证明它更可靠。[ATC 仓库](https://github.com/JSCOP/atc-kanban)

Codex 原生功能已覆盖同项目并行任务、worktree 隔离、Handoff 与持久工作区。只使用 Codex、且工作区关系简单的用户，可能没有足够理由再安装 DevMap。这是基于功能重叠的推断。[官方 Worktrees 文档](https://learn.chatgpt.com/docs/environments/git-worktrees)

## 值得验证的三个差异

1. **接入已有工作区的成本。** DevMap 可以从现存 Git 仓库开始显示，不必先在新的看板里重建任务。Vibe/ATC 文档主要围绕自己管理的任务工作区，但不能据此断言不能接入外部工作区。需实测双方的首次接入步骤与信息完整性。
2. **真实提交拓扑与未来计划共同展示。** 当前地图把工作区附着在 HEAD 上，并区分真实历史与已记录计划；长历史折叠和路径聚焦服务于这种阅读方式。本次查阅的竞品文档未建立完全等价的全局展示，但他们有 Git 状态和目标信息。地图只有降低查找时间、判断错误率时才是优势。
3. **人和 Agent 读取相同事实，并保留不确定性。** DevMap 的 MCP 暴露 workspace_facts 与 route_plans，区分缺失/过期观察；这可能减少把计划当完成、把存在当活跃的误判。MCP 并非独有，尚无对照实验说明该设计实际降低了错误。

当前最可信的定位假设是：“给已经使用多个 Agent/worktree 的开发者，一份共享的开发地图。”它可以作为现有执行工具的补充。

## 不能宣称的优势

- 跨模型：竞品已经支持多种执行器；DevMap 完整任务观察仍依赖适配器/宿主接入。
- 自动协调与更安全的合并：DevMap 本身不运行这些操作。
- Git、MCP、本地运行、npx：是基础能力或交付方式。
- 自动完整审计：结构化记录与哈希完整性不能证明所有活动都被捕获，也不能证明输入证据真实。
- 更快、更省 token、更少错误：没有相同任务、相同条件的测量。
- 已有商业壁垒：没有独立用户留存、付费或替换成本证据。

## 优先级和取舍

先完成低摩擦安装，再改善“从地图得到下一步判断”的任务流程。地图扩展、复杂术语或新的调度模块应当服从用户反馈。若用户真正需要的是创建任务、执行和合并，Vibe/ATC 可能更适合；若只是单一 Codex 工作流，宿主原生功能可能足够。

不要把只读范围一律描述成优点：它降低接入侵入性，也要求用户回到其他工具执行操作。不要把本地运行等同于独有隐私优势。

## 四周验证建议

招募 10–20 位真实使用至少三个并行工作区的开发者；分开记录 Codex 单宿主用户和混合工具用户。用相同仓库完成：
- 从五个工作区中定位某任务的真实目录与 HEAD；
- 区分已合并、未推送和仅记录的合入计划；
- 找出需要人介入的任务，并说明判断来源；
- 换一个 Agent 后恢复同一工作区的事实与计划。

交叉安排先用原有工具或先用 DevMap，记录完成时间、错误答案、求助次数、接入步骤，以及两周后是否继续使用；并记录地图误导、观察缺失和退出理由。样本量很小，只能形成产品方向信号，不能宣称普遍性能提升。

内部继续投入门槛（非行业基准）：成功安装者中一半在第二周仍用于实际项目；至少三人能指出具体节省步骤；目标任务的中位时间改善约 25%，且错误率没有上升。若没有改善，优先压缩为更轻量的工作区摘要/MCP 功能；不要用更多可视化元素掩盖需求不足。
