# DevMap 自动 Git：路线意图、合并队列与未来路线优化方案

日期：2026-09-05

当前范围修订：以 [地图优先原则与对外接口建议](2026-09-05-devmap-map-first-and-public-interface-design.md) 为准。下文自动调度与执行阶段保留为扩展研究，不再是地图版本的交付前提。

状态：用户已确认总体方向；本文细化规则为建议稿，供讨论。本文不表示相关功能已实现。

总体方向：workflow 发车时明确目的地；多条路线并行开发，进入同一目标分支时依次合并；实线只表达已发生的历史，虚线只表达尚未发生的计划。

边界细化：[路线边界、人工操作与恢复规则](2026-09-05-devmap-route-boundary-state-and-recovery-design.md) 提供状态转换、事件处理、警报和验收场景。用户已明确人工回退为准；自动化不得擅自恢复撤回内容。涉及候选更新、回退和异常处置时，以该细化文件为准。

## 1. 目标与现状

用户应能从地图回答：从哪里开始、要完成什么、现在在哪里、还剩什么、准备合入哪里、在等谁、为什么还不能合并。

2026-09-05 的本地代码核对结果：

- 当前设计目录停留在较早代码基线，不能只凭这里的 README 判断全部进展。
- Phase 1B worktree 已有 Adapter、事件采集、journal 和验收测试源码；本轮没有重跑测试。
- 后续 Dock / topology worktree 已有 Git 关系读取、工作区和任务关联、真实历史拓扑。
- 检查到的 Dock 仍使用 `NoRoutes`；未发现完整 Route Registry、自动 Git 执行器或合并队列实现。
- 现有图将虚线用于工作区关联、部分分支样式；旧设计还将虚线用于未知关系。这与本次约定冲突。
- 现有 Phase 1C.1 计划覆盖本地 branch/worktree/commit，明确延后远程 push、PR、merge。

本方案补充 2026-08-27 Orchestrator 设计，不取消既有授权、安全检查、归因和远程证据边界。实施时应修订旧计划的路线身份和字段，并更新旧图例规范；不将本文全部内容塞进 Phase 1C.1。

## 2. 最常用概念及边界

| 概念 | 产品中的含义 | 与其他概念的关系 |
| --- | --- | --- |
| Workflow / 工作流 | 完成一个目标的过程，包括开发、检查、评审和交付 | 可以包含一条或多条路线 |
| Route / 开发路线 | 一个有稳定身份、起点和交付目标的工作单元 | 简单任务默认一个 workflow 对应一条 route |
| Task / Session | 某次对话或运行中的执行上下文 | 多次会话可继续同一路线；会话不是路线身份 |
| Agent | 执行者 | 可以接手路线；Agent 结束不代表路线完成 |
| Branch | Git 中指向提交的可移动引用 | 是路线的代码载体；名称改变不应改变 route_id |
| Worktree | 实际修改和检查文件的工作目录 | 是工作空间；不是 branch 的另一种名称 |
| Commit | 已存在的代码快照及父提交关系 | 在历史层是实心站点；不直接证明需求已完成 |
| Checkpoint | 可恢复的工作状态记录 | 语义 checkpoint 不一定生成 Git commit；checkpoint commit 可以明确不完整 |
| Milestone | 一个可说明的阶段成果 | 可由多个 commit 和验证结果支撑 |
| PR | 请求评审和集成的载体 | 不是路线身份，也不是合并结果 |
| Integration target | 本次准备合入的仓库和分支 | 例如先进入 dev；不强制所有路线直达 main |
| Merge queue | 同一目标分支的合并调度队列 | 控制集成顺序，不控制各路线的开发顺序 |
| Release / Deploy | 发布与部署 | 已 merge 不等于已发布或已部署 |

默认采用简单关系：一项工作、一条路线、一个当前写入分支；需要并行独立写入时才拆子路线和 worktree。只读讨论不自动创建 branch/worktree。

Git worktree 支持同一仓库的多个工作目录；这些目录共享仓库对象，并具有各自的工作区状态。因此地图不能把它们当成独立仓库。[Git worktree 文档](https://git-scm.com/docs/git-worktree)

## 3. 路线模型：起点、当前位置、终点分别记录

### 3.1 起点

新路线在第一次写入前保存 route_id、源仓库身份、起点 commit、记录来源和创建时间。route_id 独立生成并持久化，不从 session_id、branch 名或 PR number 派生；这些都作为关联字段。

区分三种事实：

- `start_commit`：路线登记时的不可变起点。
- `observed_head`：当前观察到的分支位置，可随开发变化。
- `merge_base`：当前源与目标的共同祖先，随比较对象变化重新计算。

对接入前已有的 branch，只记录“从此处接续追踪”和已知共同祖先，不反推当时的创建意图。merge-base 可能不唯一；存在多个最佳共同祖先时显示歧义，不任意挑选一个作为历史发车站。[Git merge-base 文档](https://git-scm.com/docs/git-merge-base)

### 3.2 终点

终点由两部分组成：

1. 语义目标：完成什么，以及可检查的完成条件。
2. 集成目标：合入哪个仓库、哪个分支。

示例：完成登录修复并通过相应检查，先合入 dev；后续随发布路线进入 main。

发车时知道的是目标与条件，未来合并提交尚不存在，不能提前分配一个看似真实的 commit SHA。目标分支 HEAD 继续变化，目的地名称不因此改变；合并候选和测试依据必须更新。

目标来源优先级：明确人类指令 > 已批准路线配置 > 确定性仓库政策 > 推测建议。自动发现 dev/main 可生成建议，但不能直接成为自动合并授权。未确认目标时允许记录和安全开发，显示“终点待确认”，禁止入合并队列。

修改目标、完成条件或关键依赖时生成新的计划版本，保留旧版本及原因，并撤销受影响的候选检查和授权。修改历史本身不可覆盖。

### 3.3 生命周期不混成一个状态字段

| 维度 | 建议状态 |
| --- | --- |
| 工作进度 | planned、active、ready、abandoned |
| 集成进度（每次集成） | not_requested、queued、validating、integrating、confirmed、reconciliation_required |
| 阻塞原因 | 依赖未完成、检查失败、冲突、授权不足、目标缺失等列表 |
| 发布范围 | local、remote_confirmed、context_published |

`ready` 表示该版本的路线工作满足完成条件，不表示对最新目标分支的集成验证通过。工作区有新增未提交修改时，不能用旧 HEAD 的结果声称当前全部工作完成。

完成一次集成后，该次结果固定绑定 source SHA 与 target。相同 branch 后续又有新工作时，默认创建新路线或显式的新交付批次，不让旧的“已合并”标记覆盖新提交。

## 4. 计划与历史：同一张图的两个层次

推荐在现有真实 Git 图上增加计划覆盖层，默认展示选中路线的未来；提供“显示全部计划”开关。

| 视觉元素 | 唯一语义 |
| --- | --- |
| 实心 commit 站点、实线历史轨道 | 已观测到的 Git 对象和真实父子关系 |
| 空心计划站点、虚线计划轨道 | 尚未发生的阶段、依赖的未来安排和预计集成 |
| 当前位置标记 | 最近一次观测到的 HEAD；未提交工作以附属计数显示 |
| 锁/警告图标及短文字 | 阻塞及原因；不改变实线/虚线的含义 |
| 路线颜色与名称徽标 | 路线身份；不能再通过虚线区分分支 |
| 工作区、Agent、任务卡片 | 附着在所属站点旁；不使用轨道式连接线 |

未知关系用“未知”卡片和断开的端点表示，不补画推测连接。图的空间间距不表示剩余时间、工作量或完成百分比。

计划最少只需“当前位置 → 完成条件 → 待合入目标”。只有用户或明确计划已指定阶段时才展开中间站点，不为了填满图而编造未来 commit。

计划进展不是把虚线原样涂实：

- 一个计划里程碑可能对应多个真实 commit；实际历史按事实绘制。
- 里程碑完成后保留与实际提交/证据的映射，默认折叠已完成计划。
- 最后合入可能是 merge commit、fast-forward 或 squash，应按实际结果显示。
- Squash 的采用映射出现在详情或带明确标签的采用视图中，不能画成不存在的 Git 父子边。
- 取消路线时折叠未来计划并标记放弃，已经存在的 commit 和证据仍保留。

Git 的 fast-forward 不创建额外 merge commit；squash 不记录通常的 merge 父关系。因此“已采用”与“存在合并父边”必须分别记录。[Git merge 文档](https://git-scm.com/docs/git-merge)

## 5. 合并队列：并行开发，按目标分支串行集成

### 5.1 入队和排序

发车时登记目的地；准备就绪后才申请入队。还在开发中的路线显示“预计进入 main”，不分配真实队列序号。

队列键是规范化仓库身份和完整目标 ref，不能只用 `main` 这个名称。不同目标可以有各自队列；跨目标依赖仍需满足。

默认规则：

1. 满足入队条件后记录稳定的入队序号。
2. 调度时先排除阻塞、失效及依赖未满足的候选。
3. 在可运行候选中按入队序号处理；已授权的显式优先级优先，同级保持先后顺序。
4. 已阻塞路线保留原入队身份，其他无依赖路线可先行；解除阻塞后按原顺序参与调度。
5. 变更源提交或目标导致重新提交候选，重新进入队尾；仅重试暂时性读取失败不重置顺序。
6. 人工调序、紧急插队均记录原因，不能打断已经开始的原子集成动作。

界面分别显示“入队序号”和当前预计执行位置；等待依赖不显示成正在执行。依赖形成环时明确列出环并阻塞相关路线。

### 5.2 一次合并的完整过程

1. 读取最新源 SHA、目标 SHA、计划版本、授权版本和依赖状态。
2. 建立具体集成候选，绑定合并方式与该组 SHA。
3. 在受控的独立环境或 provider 原生队列中验证候选。无冲突仅是其中一项，还要运行配置的构建、测试、评审和 Context integrity 检查。
4. 执行前再次核对源/目标 SHA 及授权；任一变化都使受影响的结果失效。
5. 按既有 authority 和 safety gate 执行集成；下一项必须等待当前结果明确。
6. 从权威目标读取并确认结果，保存实际 SHA、方式和证据。
7. 更新地图、重新计算下一个候选；Context Bot 按原设计发布共享证据。

例：A 与 B 都在旧 main 上测试通过。A 合入后，B 必须针对包含 A 的 main 重新建立并检查候选，不能沿用旧集成测试。该过程不必修改 B 的开发分支；是否更新分支或 rebase 由独立策略和授权决定。

### 5.3 并发、外部写入与不确定结果

本地锁只能协调本机参与者，不能阻止其他机器或人工更新远端。远程自动集成必须依靠 provider 原生串行队列，或具备等价并发控制及条件更新能力的单一权威协调器。

每个目标只选一个执行所有者；若采用 provider 队列，DevMap 负责表达意图、入队、观测和展示，不再并行运行另一套自动 merge。

无法保证条件更新时，该后端只显示队列和建议，不宣称能安全自动合并。外部合并发生后重新对账；网络超时后先查询结果，不能盲目重试。远程结果尚不明确时保留“不确定”，不把计划画成已完成。

## 6. 常见场景

| 场景 | 预期处理 |
| --- | --- |
| 单人小修复 | 一条路线，已知目标；复用安全工作区，完成后入队 |
| 多 Agent 并行改代码 | 独立写入路线和 worktree；同目标完成后串行集成 |
| 切换会话、换 Agent、压缩上下文 | 继续同一 route_id；更新执行者关联 |
| A 与 B 没有依赖 | 谁先准备好谁先入队；A 阻塞不必挡住 B |
| B 依赖 A | 明确依赖 A 的成果已进入所需目标；A 未满足时 B 等待 |
| 从 A 的分支上继续开发 B | 单独记录代码基线依赖与工作依赖；A squash/rebase 后重新计算 B 候选，不能简单宣布依赖已解决 |
| feature → dev → main | 两次独立集成及各自队列；合入 dev 不标记为已进入 main |
| 工作完成但缺权限或评审 | 工作状态 ready，集成状态显示等待，不伪装成开发未完成 |
| 源分支新增提交或 force-push | 旧候选和相关证据失效，保留旧映射并创建新候选 |
| 改终点或依赖 | 版本化计划，撤销旧候选，重新检查后入新队列 |
| 目标被删除或远程身份不明确 | 阻塞并展示原因，不自动改投名称相似的分支 |
| 空分支或没有需交付的差异 | 显示无需集成，不仅凭可达性声称曾经 merge |
| Squash / rebase 合入 | 结合 provider 结果与提交映射确认采用；无法可靠对应则标记 mapping_uncertain |
| 放弃试验 | 保留实际历史，取消候选，折叠未来路线 |
| 人工回退已经合入的功能 | 以实际人工结果为基线，保留“曾经合入”的事实；保护撤回范围，显示依赖和检查影响，不自动恢复 |
| 已合入但 Context 发布失败 | Git 集成已确认、Context 待对账；不伪装成完全交付，也不重复 merge |

## 7. 对现有数据与架构的最小调整

保持 Host Adapter → Canonical Events → Orchestrator → Policy / Gate → Executor 主结构。

增加或扩展以下职责边界：

| 模块 | 职责 |
| --- | --- |
| Route Registry | 持久化路线身份、会话/分支关联及当前计划版本 |
| Route Plan | 存储目标、完成条件、阶段、依赖及版本来源 |
| Queue Coordinator | 调度候选、跟踪阻塞、委托唯一执行后端 |
| Integration Adapter | 暴露候选验证、条件执行、查询和幂等能力 |
| Integration Record | 保存 source/target/result SHA、采用方式、结果证据和不确定性 |
| Dock read model | 合并真实历史与计划视图，不执行 Git 写操作 |

建议最小数据对象：

- Route：route_id、repository_id、start_commit、start_provenance、workflow 关联、会话关联、当前分支关联、plan_revision。
- RoutePlan：route_id、revision、goal、completion_conditions、target_repository、target_ref、target_provenance、milestones、dependencies、change_cause。
- QueueEntry：entry_id、route_id、plan_revision、source_sha、target_ref、入队序号、优先级及来源、状态、阻塞原因。
- IntegrationAttempt：action_id、entry_id、expected_target_sha、source_sha、strategy、policy_revision、验证结果、provider_identity、实际结果。

Route 及计划持久化在已约定的 Git common directory 下，不放入可丢弃 Presence。计划修改采用追加事件及可重建快照；本地记录不自动等于共享权威证据，远程发布沿用 Context Bundle / Bot 边界。

PR 编号作为带 provider 和 repository 范围的外部关联，不替换 route_id。旧需求文档中“PR number 作为稳定路线键”需调整为“外部查询键”，与此次稳定路线身份统一。

已有 `merged: bool` 不能承载全部集成语义。当前 `ahead == 0` 最多证明所比较 HEAD 的可达性，不能证明实际发生过 merge、全部工作完成或 squash 结果。建议读模型区分可达性事实、采用记录及完成状态；旧客户端采用有版本的兼容投影。

## 8. 方案取舍

| 方案 | 优点 | 代价 | 建议 |
| --- | --- | --- | --- |
| 只在现有图上补虚线 | 最快看到未来方向 | 无持久化意图，重启与调度无法可靠衔接 | 只适合标明静态示意的原型 |
| 路线计划先落地，再接队列与执行器 | 数据与图一致，逐段可验收，复用现有基础 | 需要明确计划模型及兼容迁移 | 推荐 |
| 一次做完整自动交付平台 | 全链条集中完成 | 同时引入多 provider、权限、并发和恢复，范围过大 | 不作为首轮交付 |

## 9. 分阶段落地与验收

以下是交付切分，不是已执行的工程任务清单；每阶段在选定实施基线后形成独立实施计划。

### A. 路线意图与计划地图

- 整合已有 Phase 1B / topology 基础，加入持久化 RoutePlan 和真实 RouteProvider。
- 提供登记、查看、修改路线目标与关联会话的能力；不要求自动 Git 已实现。
- 替换虚线旧用途，加入空心计划站点、剩余路线、终点待确认及计划版本。
- 验收：重启与换会话不丢路线；目标变更可追溯；所有实线 Git 边都有父关系证据；未知关系不冒充计划；计划层可独立隐藏。

### B. 本地自动 Git

- 按原 Phase 1C.1 实现 branch/worktree/commit 与恢复，修正旧 session 派生 route_id 的设计。
- 自动动作绑定路线计划版本、权限和安全检查；Checkpoint 与 Milestone 区分。
- 验收：第一次写入前已登记路线；脏的未知修改不会被自动收纳；只暂存归属明确的路径；会话恢复不重复提交。

### C. 队列模型与沙箱验证

- 实现每目标队列、依赖、阻塞绕行、候选失效和幂等对账。
- 先在真实临时 Git 仓库验证执行语义；产品界面可显示待合入队列。
- 验收：A 合入后 B 重新验证；依赖环可见；目标变化不会执行旧候选；不确定结果不会触发重复集成。

### D. 远程自动交付

- 依次接入原 Phase 1C.2 push 确认、Phase 1C.3 provider 能力，再增加独立授权的远程 merge 队列集成。
- 第一轮选项目实际使用的一个 provider；其余明确标为不支持自动执行。
- 验收：外部更新与多机竞争不会覆盖未检查的目标；重试不重复创建/合并；squash 等方式保留采用映射；Context gap 可见并按原政策阻塞后续相关动作。

暂不纳入首轮：预计到站时间、智能批量合并、推测式多候选并行验证、自动历史重写、多 provider 同时交付、历史意图重建。

## 10. 建议采用的默认值

1. 一个简单 workflow 默认一条 route，需要独立并行写入才拆分。
2. 发车登记目的地；未明确时显示待确认，不编造目标。
3. 准备就绪后入队，同目标串行集成，依赖与明确优先级优先。
4. 实线为真实历史，虚线为未来计划；颜色和标签表达路线身份。
5. 默认只展开选中路线的未来，避免主图被所有计划占满。
6. 目标变更有版本，检查绑定具体候选，远端结果经确认后才显示集成成功。
7. 按 A → B → C → D 交付，先让路线记录和图的含义可靠，再扩大自动执行范围。
