# DevMap 地图优先原则与对外接口建议

日期：2026-09-05

状态：用户已明确地图优先与人工操作为准；下述接口数量和命名为讨论建议，尚未修改插件。

## 1. 当前产品定位

DevMap 以真实操作与 Git 状态为依据，提供直观的开发地图。无需预先定义人类可能进行的所有 Git 操作，也不把全部工作流程编码成强制政策。

基本准则：

1. 已确认的人类选择优先于旧计划；地图跟随实际操作，不自动恢复或撤销人的修改。
2. 实线表示实际 Git 历史；虚线表示明确记录但尚未发生的路线计划。没有计划就不编造未来路线。
3. 事实、意图、推测分别展示。不能仅凭提交标题确认操作者或回退原因；无法判断就显示未知。
4. 发现事实与计划不一致、已有证据失效或疑似回撤时，展示警报及依据，不自动干预源代码。
5. 地图中的警报不是 Git gate；确认警报只修改展示状态，不改变源仓库权限或事实。

保留真实 Git 图、路线意图、工作区/会话关联、来源证据和异常展示。合并顺序可展示用户计划或外部队列实际状态；没有执行系统提供证据时，只能称“计划顺序”。

自动 Git 执行、合并调度、WithdrawalGuard、fencing token 和强制依赖阻塞移出地图核心。若以后需要自动执行，由单独明确的执行层承接；地图观察其结果。此调整不修改任何已有执行器的安全约束，也不卸载现有采集能力。

前两份设计里的边界场景保留为数据与图示参考，不再作为地图版本必须实现的完整业务状态机或执行准入条件。

## 2. Skill、MCP 与地图界面

Skill 是可复用工作流说明；MCP tool 是模型可调用的能力；UI resource 是可展示的界面。三者数量不需要相同，一个 Skill 可以协调多个 tools，一个地图可以由多个 tools 共用。

官方依据：[插件结构](https://developers.openai.com/plugins/concepts/plugins)、[Skill 编写](https://learn.chatgpt.com/docs/build-skills)。

建议地图核心：一个 DevMap 插件、一个 Skill、一个 MCP server、三个公共 tools、一个共享地图 UI。

Skill 负责识别“看地图、刷新、解释某条路线、记录目的地”等意图，读取事实、调用正确工具，并在支持的宿主中打开界面。能力不存在时说明范围，不要求每次查看地图都录入完整需求和决策。

## 3. 三个核心工具（拟议命名）

| 工具 | 用户意图 | 行为边界 |
| --- | --- | --- |
| `devmap_open_map` | 打开地图、聚焦某条路线 | 获取当前视图并返回共享 UI；宿主能力决定展示方式；不执行源 Git 写入 |
| `devmap_read_map` | 刷新、查看状态、查询节点、解释警报 | 返回有界结构化快照或实体详情，含来源、观测时间、revision 和缺失信息；不修改路线计划 |
| `devmap_set_route_plan` | 记录/修改路线目的地和已明确的阶段 | 仅版本化写入 DevMap 计划元数据；不创建 branch、commit 或 merge，不将计划内容作为已发生事实 |

读取工具通过可选 repository_id、entity_id、view 和分页参数选择同一地图数据的范围，不发展成任意 `action` 调度器。打开工具与读取工具共用数据层，不各自生成不同事实。

路线计划工具采用显式 route_id、expected_revision 和结构化目标/阶段输入，保存指令或计划来源；新增路线返回稳定 route_id。版本冲突时返回最新版本，不能默默覆盖另一人的计划。记录计划属于元数据写入，不能标成完全只读工具。

不添加独立的 `refresh`、`explain`、`get_alerts` 工具：读取结果提供解释所需证据，由 ChatGPT 组织语言；不能据此编造历史原因。自动刷新和界面展开属于 UI/数据层交互，不必各自暴露为 Skill。

工具应按用户目标组织，并将读取与写入分开；不需要逐个映射内部模块。[官方工具设计指南](https://developers.openai.com/plugins/plan/tools)

## 4. 现状与迁移边界

本轮实际可发现一个 `live-worktree-dock` Skill 和七个 DevMap tools：

- devmap_context
- devmap_dock_snapshot
- devmap_open_dock
- devmap_start_browser_dock
- devmap_record_requirement
- devmap_record_decision
- devmap_record_evidence

建议迁移映射：context / snapshot 汇入地图读取入口；open_dock / start_browser_dock 在宿主适配层协调为统一打开入口；新增路线计划元数据入口。浏览器与 MCP App 的运行机制仍可能不同，统一的是调用意图，不承诺所有宿主拥有相同展示能力或本地仓库访问权。

已有 requirement / decision / evidence 是证据采集能力，不能被路线计划工具混用或静默删除。若完整版继续向模型暴露这三个独立记录工具，总数是六个（地图三个 + 采集三个），不是三个。地图核心版本可以只暴露三个；是否另提供采集 Skill，留到确定完整版工作流时决定，不为本轮地图新增入口。

旧接口兼容与具体发布配置在实施时单独迁移；本文没有改变当前可用的七个工具，也没有重新安装插件。

## 5. 最小验收

- 用户说“打开地图”：一个 Skill 能完成打开，不要求选择不同内部 Viewer 实现。
- 用户说“刷新并解释这个警报”：读取真实快照与证据，说明已知和未知，不执行 Git 写入。
- 用户说“这条路线最终合到 dev”：记录可追溯计划，显示虚线；不自动 merge。
- 用户人工 cherry-pick 或回退：地图反映实际变化，保留历史与必要提示，不自动补回或反向操作。
- Git 与计划不一致：事实照实显示，计划显示偏离或待更新，不强制把 Git 变回计划。
